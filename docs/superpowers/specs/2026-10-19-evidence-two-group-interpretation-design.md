# 同定候補の根拠受け渡しと2群比較の解釈 — 設計

日付: 2026-10-19（日本時間）

状態: 2026-10-19に研究者が本文を承認。実装計画を作成する段階であり、実装は未着手。

## 1. 目的と合意事項

massbank-context の目的は、MassBank RDFとの連携によって、会話側のLLMが実験結果を根拠付きで解釈できるようにすることである。
照合・情報取得・検定はそのための構成要素と位置付ける。

会話で合意した要件:

- 個々の同定候補の評価を基盤に、群間比較とスペクトル群・クラスタを解釈する。
- 初期開発では、根拠の受け渡しと**2群比較**を一緒に扱う。
- 既存のMS-DIAL等の注釈と、massbank-contextによるMassBank照合候補を両方保持する。
- スペクトル順位は保持し、生物学的妥当性は別軸で評価する。LLMやKG情報で並べ替えない。
- 試料背景は会話から抽出し、研究者が確認した内容を登録する。不明な内容を補完しない。
- 解釈はMCPを利用する会話側LLMが行う。サーバ内でLLM APIを呼ばない。
- 各主張から、実験フィーチャ、候補、取得したRDF情報へ戻れることを合格条件とする。

以降の契約・ツール名・統計への候補採用規則は、この要件を実現するための設計提案である。

## 2. 初期版の利用場面と範囲

研究者が「対照群Aと処置群Bで何が変化し、どう説明できるか」と質問する。
LLMは背景を確認し、ms-data-parserで作成した比較結果を読み、候補と関連情報を取得する。
観測事実、根拠付きの関連、生物学的仮説、限界と追加検証を分けて回答する。

含めるもの:

- 対応のある出力元IDによる、2群比較結果・既存注釈・MS/MSの接続。
- 非有意、未同定、名前だけ、MS/MSなし、複数候補、照会失敗を保持した根拠取得。
- ローカルMassBank RDF索引のレコード・化合物情報と、PubChem RDFのパスウェイ関連。
- 任意のパスウェイ濃縮・方向集計と、元の特徴量への逆参照。
- 会話側LLM向けの段階的な根拠取得と解釈手順。

初期版に含めないもの:

- 多群・時系列、新しい群間検定、候補の確率化、生物学的根拠による順位変更。
- 新しいGUI、分子ネットワーク構築、Leiden、クラスタへの候補伝播。
- HMDB・KNApSAcK等の新規接続、疾患・生理活性の網羅的取得、名称からの自動構造確定。
- 代謝物量の増減だけによる経路活性や代謝フラックスの断定。

クラスタIDを将来の関連付けに追加できる形にするが、初期版の動作検証対象は2群比較とする。
RDFの対象範囲が上記に限られることを回答にも表示し、「関連なし」と「未提供」を区別する。

## 4. 責務とデータフロー

1. 会話側LLMが研究者との会話から背景案を作る。
2. 研究者が確認した背景を、確認状態と版を付けて登録する。
3. ms-data-parserが前処理・2群比較・元形式の読込とID対応を担当し、バンドルを出力する。
4. massbank-contextがバンドルを検証し、索引照合と候補別RDF関連を取得する。
5. massbank-contextが全体の被覆、特徴量・候補別の根拠、必要なら経路集計を返す。
6. 会話側LLMが根拠IDを引用して解釈する。不足があれば詳細取得ツールを再度呼ぶ。

サーバ同士を直接呼び合わず、ms-data-parserからのファイル契約で接続する。
生の質量データの分析はms-data-parserを使い、本サーバに再実装しない。

## 5. 入力バンドル契約 v2

`manifest.json` を入口とし、同じバンドル内のUTF-8 TSVとスペクトルファイルを参照する。
版は `contract_name=massbank-context-evidence`, `contract_version=2` とする。
各参照ファイルのSHA-256、出力元解析ID、生成日時、exporter名・版をmanifestに持つ。
バンドル外への相対参照、存在しないファイル、ハッシュ不一致は読込エラーとする。

| ファイル | 主な内容 |
|---|---|
| `manifest.json` | 出力元、比較群、群別n、比較方向、前処理・検定・多重補正の条件、母集団の定義、ファイル一覧 |
| `features.tsv` | 全比較対象の `feature_id`, 元のspot ID, m/z, RT, `log2fc`, p, q, 群別平均, significant |
| `annotations.tsv` | `annotation_id`, `feature_id`, 出典、原名、InChIKey・構造ID、元の順位とスコア・判定名 |
| `spectrum_links.tsv` | `feature_id`, `spectrum_id`, 元ファイル、対応根拠、代表試料・ピークID（ある場合） |
| スペクトルファイル | 既存ローダが読めるMSP/MGF/DCL。MS/MSなしなら省略可能 |

規則:

- `feature_id` は出力元解析ID内で一意。解析IDとの複合参照を正準にし、別解析のspot IDを混同しない。
- ID対応は出力側で確定する。名前、m/z近傍、行順だけからの推測結合をしない。
- 1特徴量に0個以上の注釈、0本以上のスペクトルを許す。スペクトルファイル内IDとの照合も検証する。
- 構造IDや名前は欠測を許す。名称一致だけでInChIKeyを割り当てない。
- `log2fc_sign` は `positive means group_b is higher` を必須とし、不一致は拒否する。
- 欠測数値は空欄で表す。NaN/Infinity、不正なp/q、重複ID、壊れた参照を拒否する。
- significantは上流の判定を保持する。条件もmanifestに残し、LLMや本サーバが再判定しない。
- 比較対象は前処理後の全フィーチャ。前処理で除いた対象は元の総数・段階別件数・理由を記録する。
- 全フィーチャにIDがあり、件数・候補・スペクトル対応の整合性が確認できたときだけ `population_complete=true`。

## 6. 根拠モデルと背景確認

根拠は、バンドルのハッシュに基づく `analysis_id` と、由来ごとの安定したIDを持つ。
`feature_id`, `candidate_id`, `evidence_id`, `lookup_id`, `context_revision` で参照する。
IDは取得順やページ位置で変わらない。生成規則は契約テストで固定する。

候補は出典別に保持し、同じInChIKeyでも元の候補を消さず `same_structure_as` で関連付ける。
既存注釈の順位・評価値と、MassBankのweighted_score等を共通スコアへ変換しない。
同点、異性体、`PRECURSOR_ONLY`、既存注釈との不一致を明示する。
表示上のtop-kだけで全候補が一意と判断せず、取得範囲と打切りを持つ。

MassBank根拠にはaccession、化合物名・構造ID、測定条件、索引の版・構築時刻・照合条件、元TTL参照とライセンスを持つ。
元TTL参照を復元できない既存索引では、その項目を欠測として示す。架空のリンクを作らない。
PubChem根拠には対象InChIKey、返却URI、関係述語、種情報、endpoint、クエリ版、取得時刻を持つ。
取得関係は `has participant` として扱い、基質・産物・反応方向へ読み替えない。

照会状態は `not_queried / resolved / empty / failed / unsupported_identifier` を区別する。
生物種が不明・不一致の関係は補足表示できるが、種を指定した経路検定には混ぜない。

背景は生物種・組織・処置・群の意味・測定条件・研究上の問いを保持する。
各項目に値、ユーザー由来の説明、`proposed/confirmed` を持ち、不明はnullとする。
会話側LLMは確認済み版だけを解釈の前提に使う。サーバの記録は確認申告であり、本人確認を保証するものではない。
背景変更時は版を進め、旧版で作成した解釈が現行版に基づくように表示しない。

## 7. 2群の事実集計とパスウェイ検定

全特徴量の上昇・低下・有意・欠測と、候補・MS/MS・RDFの被覆を別々に返す。
有意な特徴量だけを読んで全体の傾向や被覆を算出しない。単なる非有意を同等性の証拠としない。

パスウェイ検定は任意であり、失敗や低被覆でも個々の候補評価・比較結果の説明を妨げない。
初期版の新フローでは、次の保守的な統計用射影を使う:

- 元の候補をすべて保持したまま、出力済みの構造候補が1つのfull InChIKeyに一致する特徴量だけを採用する。
- 既存注釈だけで構造IDが一意な場合も採用できるが、MS/MS未検証を明示する。
- 候補競合、候補取得打切り、名前のみ、比較値欠測の特徴量は検定から除外し、件数と理由を返す。
- LLMの「もっともらしさ」によって採用候補を選ばない。この規則は同定確定や同定確率を意味しない。
- 同じInChIKeyの複数特徴量は、符号が競合すれば方向不一致として検定から除外する。
- 競合しない重複は現行の「significant優先、次に絶対log2FC最大」で代表化し、全元IDと採用行を残す。
- ここまでの採用対象について照会が完了し、指定生物種のパスウェイを持つ化合物を背景とする。
- 全入力、統計採用、照会完了、種適合、経路付与、実際の検定背景の件数を分けて返す。
- Fisher + BHと方向記述・Wilcoxonは既存の純関数を再利用し、合成スコアを作らない。

照会失敗・未照会が採用対象に残る間は検定結果を返さず、再照会対象を示す。
曖昧な候補による解釈は仮説として残せるが、有意性を付与しない。
候補採用・重複処理規則を結果に毎回明記し、既存v1の検定結果と同じ集計だと見せない。

## 8. MCPインターフェースと取得量

新ツールの提案:

| ツール | 責務 |
|---|---|
| `load_evidence_bundle(path)` | バンドル検証とanalysis_idの発行、母集団・入力欠落の概要 |
| `set_analysis_context(analysis_id, context, confirmed)` | 背景案・確認済み背景の版管理 |
| `match_feature_spectra(analysis_id, feature_ids, top_k)` | 対応済みスペクトルを既存エンジンで照合し、候補・条件を保持 |
| `resolve_candidate_evidence(analysis_id, candidate_ids, refresh=False)` | ローカルメタデータとPubChem関連の取得・照会状態の記録 |
| `get_comparison_evidence(analysis_id, feature_ids, cursor, limit)` | 全体集計、または指定特徴量の型付き根拠をページ単位で取得 |
| `draft_comparison_findings(analysis_id, organism, include_pathways=False, exclude_feature_ids=None)` | 参照可能な事実と仮説スロット、制約、任意の経路集計（`exclude_feature_ids` は 2026-11-16 に追加。§13） |

既存の8ツールは維持する。新ツールは内部の型付きサービスを利用し、公開TSVを再パースしない。
詳細取得は既定50特徴量・最大200、候補照合top_kは既定5・最大20とする。
有意結果の優先表示は可能だが、全件取得経路と全件ベースの概要を必ず残す。
戻り値に件数、選択条件、`truncated`、次cursor、未処理対象を載せる。
照合top-k境界の同点は件数と打切り状態を示し、一意候補と誤認させない。

サーバにLLM SDK依存を追加しない。巨大なピーク列は返さず、必要なときに既存のinspectを使う。
新しい中間状態は索引とは別のローカル成果物領域に保存し、サーバ再起動後もanalysis_idで再読込可能とする。
結果の版はバンドルハッシュ・照合条件と索引版・照会スナップショットで識別する。
入力変更は別analysis_id、照合・refresh更新は別根拠版とし、旧版を上書き参照しない。
cursorに版を含め、異なる版のページを混在させない。公開層は既存のコンパクト直列化規約に従う。

## 9. 会話側LLMへの手順と根拠の引用

リポジトリ内に利用手順を置き、MCPツールのdocstringからも必要な順序・注意事項を伝える。
通常は背景確認、入力検証、全体概要、候補照合、根拠取得、詳細取得、解釈の順に進む。
MS/MSがない特徴量では照合をスキップし、そのまま既存候補の根拠を取得できる。

回答の構成:

1. 観測事実: 群名・比較方向・効果量・統計結果。feature_idを引用する。
2. 候補と根拠: 既存注釈と照合の整合・競合。candidate_id/evidence_idを引用する。
3. 解釈仮説: 候補が変わっても成立する説明と、特定候補に依存する説明を分ける。
4. 限界と追加検証: 未同定・被覆・欠測、対立仮説、確認する測定や解析を示す。

LLMの一般知識は `model_knowledge` として分け、RDFから取得した事実に見せない。
引用IDの存在と参照先の一致は機械的に検証可能とする。意味の妥当性は研究者のレビューが必要であり、引用だけで保証しない。

## 10. 状態・障害・外部通信

入力・対応不整合は根拠生成前に拒否する。再読込失敗で旧解析を新解析として返さない。
未確認背景では事実取得を許すが、背景に依存する解釈の準備未完了を示す。
索引なし・互換層なし・MS/MSなし・候補なしを別状態にし、既存注釈や群間事実は取得可能とする。
照会失敗時も取得済みの根拠を提示できるが、完全な被覆や検定結果として扱わない。

外部送信はPubChemへ照会する構造IDに限る。試料背景、群名、強度、ファイルパスは送信しない。
既存キャッシュを利用し、refreshによる取得日時・根拠版の変化を明示する。
新しい根拠ストアはendpointとクエリ版を区別し、別endpointの結果を混ぜない。
古いキャッシュで不足する述語URI等は取得方法の来歴とともに補い、復元できない来歴は欠測とする。
解析成果物・入力・確認済み背景はGit追跡外とし、研究データを設計書やfixtureに複写しない。

## 11. 検証と完了条件

合成fixtureによる契約・回帰検証:

- 全特徴量の保持、比較方向、欠測・不正値、ファイルハッシュ、異なる解析IDの誤結合拒否。
- 既存候補とMassBank候補の一致・競合・同点・複数スペクトル・MS/MSなし。
- 名前のみ、索引外の既存候補、未照会・empty・failed、種不一致の区別。
- 生物学的背景を変えてもスペクトル順位・スコアが変わらないこと。
- 統計用採用・除外・重複・逆方向スポット、非有意を含む母集団、版・cursor・参照整合性。
- 索引・endpoint・refresh・入力・背景変更時の版管理と再起動後の再読込。
- 既存v1と8ツールの回帰、上限・打切り・情報欠落の明示、機密情報を外部へ送らないこと。

実経路の検証:

- ms-data-parserの実MCP出力から読込・照合・根拠取得まで通す。
- 公開または研究者が指定した2群データを固定し、条件や候補を結果に合わせて調整しない。
- 競合候補・MS/MSなし・RDFヒットなしを含む対象を確認する。実データにない端点はfixtureで補う。
- 会話側LLMの入力根拠版・実際の回答・モデルと取得可能な設定を保存し、研究者が主張と根拠を点検する。
- 群方向の逆転、候補の混同、存在しない根拠の引用、検索失敗の否定的証拠化を許容しない。
- 未支持の活性断定を観測事実として出さず、候補依存性と被覆不足を説明する。

完了には、コードのテスト成功に加えて、実MCP経路とLLM回答のレビューを要する。
LLM回答の科学的妥当性はテスト成功だけでは確定しない。

## 12. 実装計画へ渡す単位

1. ms-data-parserとのv2 export契約・実在ID対応の確認と合成バンドル。
2. 全特徴量・候補・背景・来歴のモデル、ローカル保存と版管理。
3. スペクトル対応・既存照合の型付き再利用、MassBankメタデータ取得。
4. 候補ごとのPubChem根拠取得と、状態・来歴の保持。
5. 2群集計・保守的な統計用射影・根拠取得/提示ツール。
6. 会話側の利用手順、実MCP統合検証、固定した実例での解釈レビュー。

この順序は依存関係を示す。根拠受け渡しだけを完成扱いにせず、2群比較の解釈までを一つの到達点とする。
実装計画の作成と実装開始は、本文のレビュー後に行う。

## 13. 事実確認の記録と、その後の変更（2026-11-13 確認、2026-11-16 記録）

外部の指摘（T34・T35・M36〜M41）を 2026-11-13 にコードと実データで確かめた。直すかどうかはユーザーが 2026-11-16 に決めた。

### 13.1 経路集計の生物種の照合（修正済み、コミット `0fae999`）

背景の species は手順書どおり `10090`、PubChem RDF の生物種 URI の末尾は `TAXID10090` で、文字列のまま比べていた。そのため実データでは
`draft_comparison_findings` の経路集計が必ず `no_species_pathways` になっていた。合成の縦断テストが偽の URI（`http://example.org/10090`）を使っていて
気づけなかった。`taxid_key` で `TAXID` の接頭辞を外してそろえ、背景と `organism` はどちらの書式でもよくした。2026-10-19 の実経路の検証
（§11）の経路集計の 0 件は、このバグの影響を受けている。

### 13.2 T34: パスウェイの被覆（事実。記録のみ）

腎臓の加齢の実データ（Git 追跡外の検証の根拠ストアで計算し直した。マウス）:

| | 陽イオン | 陰イオン |
|---|---|---|
| 全特徴 / 統計用射影の化合物 | 2,123 / 1,178 | 1,510 / 553 |
| 照会した InChIKey のうち、どれかの生物種のパスウェイが付いたもの | 32 / 1,364（2.3%） | 46 / 1,532（3.0%） |
| うちマウスのパスウェイ | 5（0.4%） | 20（1.3%） |
| 射影の化合物でマウスのパスウェイを持つもの（13.1 の修正後） | 0 | 1（パスウェイ 2 件、`min_members` 未満で未検定） |

パスウェイ設計書 §3.2 の 14.5% は索引の InChIKey の無作為標本の値で、実験の化合物（脂質が多い）ではずっと低い。原因は PubChem の注釈の不在で、
コードでは上げられない。索引の ClassyFire の分類も、射影の化合物のうち完全な InChIKey で 2〜3%（先頭ブロックだけでも約 12%）しか覆わないので、
代わりにならない。ユーザーの決定（2026-11-16「記録のみ」）でここに記録するだけにした。§7 のとおり、低被覆でも個々の候補と比較の説明は妨げない。

### 13.3 T35: 経路集計の入力から特徴量を除く口（追加）

`draft_comparison_findings` に `exclude_feature_ids` を足した。統計用射影の前に除き、理由 `caller_excluded` として `pathways.exclusion_counts` に数える
（理由の判定では最初に見る）。事実（全特徴量の集計とページ）は変えない。外来の分子の走査で A・B になった特徴量を経路集計から除く、といった使い方を想定する。
黙って無視しないため、未知の ID と、`include_pathways=False` での指定は誤りにする。旧来の `pathway_activity`（v1）には足していない（§3: v1 は互換を保ち、新機能は新しいツールで出す）。

### 13.4 M36〜M41: 会話側 LLM への制約（事実。変えない）

ユーザーの決定（2026-11-16「変えない」）で、仕組みは変えず、どこまで効いているかをここに記録する。

| 指摘 | 確かめた事実 |
|---|---|
| M36 `analysis_id` を毎回渡させる | 根拠系 6 本（`set_analysis_context`・`match_feature_spectra`・`resolve_candidate_evidence`・`get_comparison_evidence`・`draft_comparison_findings`・`validate_comparison_claims`）と外来の分子の 3 本で必須、既定値は無い（§8 の再起動後の再読込と、別解析の混同の防止のため）。旧来のパスウェイ系 4 本（`load_differential`・`resolve_pathways`・`pathway_activity`・`draft_pathway_findings`）は `analysis_id` を取らず、プロセス内の状態を使う |
| M38・M39 `confirmed` で経路集計を閉じる | `draft_comparison_findings` の経路集計は、背景の `status` と species がともに `confirmed` で、taxid が `organism` と一致するときだけ走る。`confirmed=True` は呼び出し側が立て、サーバが確かめるのは値ごとの `source` が空でないことだけ（§6 のとおり確認申告で、本人確認ではない）。旧来の `pathway_activity` にこの制限は無い |
| M40 空の仮説の欄を返し、語を制限する | 両系統の `draft_*_findings` が空の仮説スロットを返す。「活性化」などの語の制限は、サーバ自身が書く facts をテスト（`tests/test_report.py`）で確かめているだけで、会話側 LLM の文章は検査しない（サーバは文章を受け取らない） |
| M41 引用の様式を強いる | 強いていない。`validate_comparison_claims` は任意で（`next_actions` が勧めるだけ）、ID の実在と対応・版の一致だけを見る。ID を 1 つも引用しない主張も `valid=true` になる。§9 の「機械的に検証可能とする」の範囲であり、意味の妥当性は研究者のレビューに残る |
